# 管理画面ロール権限設計

作成日: 2026-09-12
関連: [プロジェクト方針とやりたいこと整理](20260912_1528_プロジェクト方針とやりたいこと整理.md) の「C. 管理画面のロール権限」

---

## 1. 目的

議員・市長側に管理画面を使ってもらうための権限設計。目的は2つ。

1. **議案データの妥当性検証と修正** — スクレイパーが取り込んだデータの正確性は、当事者である議員が一番分かる
2. **会派見解の移譲** — 今は運営者が各会派の見解を書いているため「あの会派の見解は運営者の解釈だ」と言われうる。
   当の会派が自分で書けばその疑念が消える。**プラットフォーマーとして声を選別しない立ち位置の直接的な実装**

あわせて、出馬者（立候補予定者）に市民のインタビュー内容を読んでもらう。
「多様な民意を、議会に届け、反映する」という哲学の、最も分かりやすい実装がここ。

## 2. 現状の実装

### 認証・認可

| 項目 | 現状 |
|---|---|
| ロールの保持先 | GoTrue の `app_metadata.roles` 配列（`admin/src/lib/auth/permissions.ts:7`） |
| 判定関数 | `checkAdminPermission()` のみ実質稼働。`checkEditorPermission()` は「将来的に使用」コメント付きの**空の器**（同 :12-18） |
| ルート保護 | `admin/src/middleware.ts` が全ルートで `checkAdminPermission` を実行し、非adminは `/login` へリダイレクト |
| アクション保護 | `requireAdmin()` を各 Server Action の先頭で呼ぶ（**約40箇所**） |

| 変更履歴 | **存在しない**（`created_by` / `updated_by` 列も監査テーブルも無い。`preview_tokens.created_by` のみ例外） |

### 設計時に見つかった既存の問題

> **`upsertStance()` と `deleteStance()` に認可チェックが無い。**
> （`admin/src/features/faction-stances/server/actions/upsert-stance.ts`、`delete-stance.ts`）
>
> どちらも `"use server"` の Server Action でありながら `requireAdmin()` を呼ばず、
> いきなり `createAdminClient()`（Service Role）で書き込んでいる。
> Server Action のエンドポイントは Action ID を知っていれば外部から叩けるため、
> **未認証で会派見解を改ざんできる状態**。他の約40箇所は `requireAdmin()` を呼んでいるので、この2つだけが抜けている。
>
> これは今回のロール対応とは独立した既存の不具合だが、**議員にアカウントを配る前に必ず塞ぐ**。
> 会派見解はまさに議員に移譲する対象であり、ここが無防備なままでは移譲そのものが成立しない。

## 3. ロール定義

| ロール | 対象 | 用途 |
|---|---|---|
| `admin` | 運営者本人 | 全権。アカウント発行はこのロールのみ |
| `legislator` | 議員 | 議案マスタの修正 ＋ **自会派の**見解編集 ＋ インタビュー閲覧 |
| `candidate` | 出馬者（立候補予定者） | 閲覧のみ |

- 1ユーザー1ロール（配列ではなく単一値）。現状の `roles` 配列は使わない
- `legislator` は**必ず1つの会派に紐づく**
- `candidate` は会派に紐づかない（無所属の立候補予定者がありうるため `faction_id` は null 可）
- 選挙後に `candidate` → `legislator` へ変更する運用が発生する（後述）

### この切り分けの根拠

- **議員に開くのは4つ** — 議案マスタ / 議案コンテンツ / 議案へのタグ付け / **自会派の**見解
- **議案コンテンツを開くリスクは、認識したうえで受け入れる**。
  これは市民の目に触れる説明文であり、書きようによっては**印象操作が可能**。
  だからこそ**変更履歴を必ず残す**。権限を閉じてリスクを避けるのではなく、
  **記録によって検証可能にする**方向を選んだ。これは「声を選別しないプラットフォーマー」という
  立ち位置とも整合する — 編集させないのではなく、誰が何を変えたかを明らかにする
- **タグ付けは履歴を残さない**。分類の付け替えであり印象操作の余地が小さく、
  誤りがあっても画面上すぐ気づける。記録する価値に対してノイズが多い
- **公開/非公開は admin のみ**。議員に渡すと「自会派に不利な議案を隠す」余地が生まれる
- **破壊的操作（作成・削除・マージ）は admin のみ**。取り返しがつかないため
- **インタビューは生ログまで全ロールに開く**（決定済み）。
  アクセス制御ではなく**市民への事前告知と同意**でカバーする設計
  （[方針ドキュメント §8](20260912_1528_プロジェクト方針とやりたいこと整理.md) 参照）

## 5. DB設計

### 5-1. `admin_profiles`（新設）

ロールと会派の紐付けを持つ。`app_metadata` に押し込むより、SQL で引けて外部キーが張れるこちらを採る。

```sql
create table public.admin_profiles (
  user_id uuid primary key references auth.users(id) on delete cascade,
  role text not null check (role in ('admin', 'legislator', 'candidate')),
  faction_id uuid references public.factions(id) on delete restrict,
  display_name text not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  -- legislator は必ず会派に属し、それ以外は会派を持たない
  constraint admin_profiles_faction_required
    check (
      (role = 'legislator' and faction_id is not null)
      or (role <> 'legislator' and faction_id is null)
    )
);

alter table public.admin_profiles enable row level security;  -- ポリシーは定義しない

create index admin_profiles_role_idx on public.admin_profiles (role);
create index admin_profiles_faction_id_idx on public.admin_profiles (faction_id);
```

- `on delete cascade`: auth ユーザーを消せばプロフィールも消える
- `faction_id` は `on delete restrict`: 議員が紐づく会派を誤って削除できないようにする
- `display_name`: 監査ログの表示や画面のヘッダーに使う。メールアドレスだけだと誰か分からない

### 5-2. `admin_audit_logs`（新設）

**議員に編集権を渡す以上、必須。**
目的は不正の検出よりも**疑念の防止**にある。他会派から「A党が議案の説明を書き換えたのでは」と
言われた時に、履歴が無いと反証できない。中立プラットフォームを名乗るための担保。

```sql
create table public.admin_audit_logs (
  id uuid primary key default gen_random_uuid(),
  actor_user_id uuid not null,            -- FKは張らない（ユーザー削除後も履歴を残す）
  actor_email text not null,              -- 実行時点のスナップショット
  actor_role text not null,               -- 実行時点のロール（後で変わっても履歴は当時のまま）
  actor_faction_id uuid,                  -- 実行時点の所属会派
  action text not null,                   -- 例: 'bill.update', 'faction_stance.upsert'
  target_table text not null,
  target_id uuid,
  before_data jsonb,                      -- 変更前（作成時は null）
  after_data jsonb,                       -- 変更後（削除時は null）
  created_at timestamptz not null default now()
);

alter table public.admin_audit_logs enable row level security;  -- ポリシーは定義しない

create index admin_audit_logs_created_at_idx on public.admin_audit_logs (created_at desc);
create index admin_audit_logs_target_idx on public.admin_audit_logs (target_table, target_id);
create index admin_audit_logs_actor_idx on public.admin_audit_logs (actor_user_id);
```

**設計上の判断:**

- **actor の情報はスナップショットで持つ**（FKで参照しない）。
  ロール変更や退任でユーザーが消えても、当時の記録は当時のまま残す必要がある
- **差分ではなく before/after を丸ごと jsonb で持つ**。実装が単純で、後からどんな比較もできる。
  実測で `bill_contents` は1行あたり平均 2.5KB（最大 3.5KB）なのでサイズ上の問題も無い

### 記録対象

| 対象 | 記録 | 理由 |
|---|:--:|---|
| `bill_contents`（議案コンテンツ） | **必須** | 市民の目に触れる説明文。書きようによって印象操作が可能。**ここが監査ログの主目的** |
| `bills`（議案マスタ） | 必須 | 議決結果など事実関係。誤りが残ると信頼を損なう |
| `faction_stances`（会派見解） | 必須 | 他会派からの疑念に反証する必要がある |
| `bills_tags`（議案へのタグ付け） | **対象外** | 分類の付け替え。印象操作の余地が小さく、画面上すぐ気づける |
| マスタ類（定例会・会派・委員会・タグ定義） | 任意 | admin のみが触る。記録コストは小さいので入れてよいが優先度は低い |
| 閲覧操作 | 対象外 | 量が膨らむ割に使い道が薄い |

### 保持期間: 無期限（削除処理を作らない）

判断の根拠:

- **容量が制約にならない** — before/after を持っても1編集あたり約5KB。
  議案を年300〜400件、各3回編集と見積もって年1,000編集でも **年20MB程度**。
  議員任期の4年でも 80MB で、VPS のディスクに対して無視できる
- **目的から逆算すると長期保持が正しい** — 「印象操作の検証」が目的である以上、
  **古い改変こそ検証できる必要がある**。古いものから消す設計は目的そのものに反する。
  ここが通常のアプリケーションログとの決定的な違い
- **意味のある区切りは議員任期の4年** — 選挙のたびに「前期に何をしたか」が問われるため、最低1期分は必須
- **実装コストが最小** — 削除処理もバッチも不要
- **逆方向の考慮** — `actor_email` は個人情報。ただし公職者が職務として行った編集の記録であり機微性は低い

**運用トリガー**: `admin_audit_logs` が 1GB を超えたら方針を見直す。上の見積もりでは数十年到達しない。

> **未決**: 退任者の `actor_email` を将来どう扱うか（匿名化するか、そのまま残すか）。

## 6. 認可の実装方針

### 6-1. middleware は「認証」だけを担当する

現状 `admin/src/middleware.ts` が `checkAdminPermission` で認可まで行っているが、**認可は middleware から外す**。

理由:

- `admin_profiles` をDBに置くと middleware から毎リクエスト DB を引くことになり、重い
- middleware を認可の唯一の砦にすると、matcher の設定漏れがそのまま権限漏れになる
- Server Component / Server Action 側で判定する方が、対象データに近く条件も書きやすい

変更後の役割分担:

| 層 | 責務 |
|---|---|
| `middleware.ts` | セッション更新と**ログイン済みかどうか**のみ。未ログインは `/login` へ |
| `(protected)/layout.tsx` | `admin_profiles` にレコードがあるか確認。無ければ `/login?error=unauthorized` |
| 各 `page.tsx` | そのページに必要なロールを `requireRole()` で要求 |
| 各 Server Action | **必ず先頭で** `requireRole()` を呼ぶ。UIを隠すだけでは不十分 |

### 6-2. `requireRole()` を追加し、既存の `requireAdmin()` は温存する

`admin/src/features/auth/server/lib/auth-server.ts` を拡張する。

```ts
export type AdminRole = "admin" | "legislator" | "candidate";

export type AdminUser = {
  id: string;
  email: string;
  role: AdminRole;
  factionId: string | null;
  displayName: string;
};

/** ログイン中のユーザーとプロフィールを取得。管理画面の利用資格が無ければ null */
export async function getCurrentAdminUser(): Promise<AdminUser | null>;

/** 指定ロールのいずれかであることを要求する。満たさなければ throw */
export async function requireRole(allowed: AdminRole[]): Promise<AdminUser>;

/** admin 限定。requireRole(["admin"]) のエイリアス */
export async function requireAdmin(): Promise<AdminUser>;
```

**移行が安全になる設計になっている点が重要**:

既存の約40箇所はすべて `requireAdmin()` を呼んでいる。
`requireAdmin()` の意味を「admin ロールのみ」に定義すれば、**手を入れなかった箇所は自動的に最も厳しい権限のまま**残る。
議員に開きたい箇所だけを `requireRole(["admin", "legislator"])` に**明示的に**書き換えればよい。
つまり、書き換え漏れは「権限が開きすぎる」方向ではなく「閉じすぎる」方向に倒れる。

### 6-3. 会派スコープ（自会派のみ編集可）

会派見解の書き込みは、対象の `faction_id` が実行者の所属会派と一致するかを検証する。

```ts
/** 会派見解を編集する資格があるか検証し、無ければ throw */
export async function requireFactionStanceAccess(factionId: string) {
  const user = await requireRole(["admin", "legislator"]);

  // admin は全会派を編集できる
  if (user.role === "admin") return user;

  if (user.factionId !== factionId) {
    throw new Error("自分が所属する会派の見解のみ編集できます");
  }

  return user;
}
```

`deleteStance(stanceId)` は引数に `faction_id` を持たないため、**削除前に対象行を取得して会派を確認する**必要がある。

UI 側も、議員には自会派の見解欄のみ編集可能にし、他会派は読み取り専用で表示する。
（他会派の見解が見えること自体は問題ない。公開情報なので）

### 6-4. 純粋関数の切り出し

判定ロジックは外部依存を持たない純粋関数として切り出し、テストを書く
（[CLAUDE.md](../CLAUDE.md) の「純粋関数の切り出し」ルール）。

配置: `admin/src/features/auth/shared/utils/`

| 関数 | 責務 |
|---|---|
| `canAccessPage(role, path)` | ロールとパスから画面アクセス可否を返す |
| `canEditFactionStance(user, factionId)` | 会派見解の編集可否 |
| `isAllowedRole(role, allowed)` | ロール判定 |

ナビゲーションの出し分けも `canAccessPage` を使い、**画面定義と判定ロジックを1箇所に集約**する。

- ローカル開発では Supabase の Mailpit（`http://127.0.0.1:54124`）でメールを確認できる

### SMTP について

招待機能（`createAdmin`）が既にあるため、SMTP は元々必要だった要件。
パスワードリセットと同時に整備する。議員宛のメールが Gmail から飛ぶのと
ドメインメールから飛ぶのとでは、信頼性も到達率も違う。

## 8. アカウント発行の運用

- **発行できるのは admin のみ**（＝運営者本人）
- 現在の `createAdmin()` はパスワードを直接指定して作成する方式。
  外部の人に配るなら**招待メール方式**（GoTrue の `inviteUserByEmail`）に変える。
  運営者が相手のパスワードを知っている状態を作らない
- `/admins` 画面を拡張し、**ロールと会派を指定して招待**できるようにする
- 一覧に `display_name` / ロール / 会派 を表示する（今はメールアドレスのみ）

### 本人確認

技術ではなく運用で担保する。**議会事務局を通すか、公式に公開されている連絡先宛に招待を送る**。
自己申告のメールアドレスに送らない。

### 選挙後のロール変更

`candidate` → `legislator` への変更時は `faction_id` の設定が必須になる（CHECK制約で強制）。
落選・引退時は削除ではなく、まず権限を落とす運用を推奨（監査ログの actor は残る）。

> **未決**: 任期・改選のタイミングで棚卸しする手順を決める必要がある。
> 議員でなくなった人がアカウントを持ち続ける状態を防ぐ。

## 9. 実装フェーズ

## 10. セキュリティの多層構成

外部の人が管理画面に入るが、Basic認証を捨てるのではなく
**共通のBasic認証 → 個別ログイン の2層**にする。

| 層 | 認証単位 | 目的 |
|---|---|---|
| Basic認証 | **全員共通の1組** | 管理画面を公開URLに素で晒さない。スキャン・総当たり・クローラを入口で落とす |
| Supabase Auth | **個人ごと** | 本人特定とロール判定。監査ログの actor はこちら |

Basic認証のIDとパスワードは議員・出馬者に共通で周知する。
その内側で、ログイン画面から各自が個別のアカウントで入る。

### 現状と実装方針

- Basic認証は **web にのみ実装されている**（`web/src/lib/basic-auth.ts` ＋ `web/src/middleware.ts`）。
  **admin には無いため新規実装**。ただし web に完成品があるので作業は小さい
- 純粋関数（`parseBasicAuth` / `validateBasicAuthHeader` / `isHtmlAcceptHeader`）は
  `packages/shared` に移して両アプリから使う。`NextRequest` に依存する薄いラッパーだけ各アプリに置く
- **nginx ではなくアプリの middleware に置く**。admin は VPS とローカルの両方で動かすため、
  環境によって挙動が変わらない方がよい

### 実装上の注意（必須）

**HTMLナビゲーションのみを challenge 対象にする。**

admin は自分自身のAPIを呼んでいる。
`run-topic-analysis-action.ts:26` → `/api/topic-analysis/run`、
`trigger-next-phase.ts:27` → 各フェーズのエンドポイント。
いずれも `REVALIDATE_SECRET` を Bearer で送るサーバー間通信であり、
**全リクエストを challenge すると 401 で壊れる**。

web の実装は Accept ヘッダを見て HTML ナビゲーションだけを対象にしているので、同じ方式を踏襲する。

### 割り切る点

- **共通パスワードは「本当のセキュリティ」ではない。** 共有された時点でグループチャットやスクショに残る。
  ボットとスキャンを落とす入口フィルタと位置づけ、データを守るのは個別ログイン・権限・監査ログ
- **退任時にローテーションが必要。** 誰かが抜けたら共通パスワードを変えて全員に再周知する手作業が発生する。
  人数が増えるほど面倒になり、実際にはローテーションされなくなりがち
- **議員にはパスワード入力が2回発生する。** 1回目はブランディングの無いブラウザ標準ダイアログ。
  使ってもらいたい相手にとっては離脱要因になりうるため、案内文を丁寧に用意する
  （ブラウザが記憶するので毎回ではない旨も添える）

### その他

- admin は VPS とローカルの両方で動かす構成
  （[方針ドキュメント §5](20260912_1528_プロジェクト方針とやりたいこと整理.md)）。
  Claude CLI 依存の機能は admin ロール限定なので、議員の画面には出ない
- ログイン試行のレート制限、セッション有効期限の見直しが必要かを別途検討する

**IP制限は掛けない**（確定）。議員がどこからアクセスするか分からないため。
Basic認証を入り口に置くことで、その分の担保とする。

## 11. 決定事項とその理由

設計中に確認し、決定した項目の記録。

| 論点 | 決定 | 理由 |
|---|---|---|
| 議員の編集範囲 | 議案マスタ・**議案コンテンツ**・**タグ付け**・自会派の見解 | 妥当性検証を実効的にするため広めに開く。コンテンツのリスクは履歴で担保 |
| 議案コンテンツの履歴 | **必ず残す** | 市民の目に触れるため印象操作が可能。閉じるのではなく検証可能にする |
| タグ付けの履歴 | **残さない** | 印象操作の余地が小さく、画面上すぐ気づける |
| 出馬者の閲覧範囲 | 議案一覧・詳細も閲覧可 | インタビューを読むには議案の文脈が要る |
| 議員アカウントの単位 | **個人ごと**（会派共用にしない） | 印象操作的な編集があった場合に**個人を特定する必要がある**ため |
| 監査ログの保持期間 | 無期限 | 容量が制約にならず、古い改変こそ検証対象であるため |
| IP制限 | 掛けない | 議員のアクセス元が不定。Basic認証で代替 |
| Basic認証 | 共通1組を周知し、内側で個別ログイン | 管理画面を公開URLに素で晒さないための入口フィルタ |

### 残る未決

- 退任者の `actor_email` の扱い（匿名化するか）
- 任期・改選時のアカウント棚卸し手順
- ログイン試行のレート制限、セッション有効期限の見直しの要否
