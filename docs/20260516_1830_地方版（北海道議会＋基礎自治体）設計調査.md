# 地方版（北海道議会＋基礎自治体セレクト）設計調査

- 作成日: 2026-05-16
- 起案者: Claude（調査・整理）／shuig（決定）
- ステータス: 調査・初版（実装着手前のレビュー対象）

## 0. 本ドキュメントの目的とスコープ

本家 `mirai-gikai`（国会版）の派生として、**北海道議会版**を新規構築する。
- デフォルト表示は「北海道議会」の議案。
- 画面上のセレクトボタンで**北海道内の基礎自治体**（道内全179市町村）に切り替えられる。
- 選択した自治体の議案・情報が一覧/詳細で表示される。

本ドキュメントは、

1. 本家の国会前提がどこに埋め込まれているか
2. 既存の地方版実装（`mirai-gikai-fukuoka-city`、いわゆる「福岡市版」）が何をどう変えたか
3. その差分を踏まえ、北海道議会＋複数基礎自治体を扱うために**追加で必要な改修**

を網羅的に洗い出すことを目的とする。実装計画書（タスク分割）はこの調査をもとに別途作成する。

## 1. 前提となる方針決定（ユーザー合意済み）

| 論点 | 採用方針 |
|---|---|
| テナント分離 | **共通DB + `scope_id` 方式**（1 Supabase、1 Web、1 Admin。URL/Cookieでscope切替） |
| MVPスコープ | **北海道議会＋道内全179市町村**（道議会と市町村セレクタが最初から共存） |
| データ収集 | **当面は手動入力＋MCPツール経由**（スクレイパー自動化は後回し） |
| 政党・会派スタンス | **福岡市版で導入済みの `factions` + `faction_stances`** を踏襲（`mirai_stances` は廃止） |

これに伴うアーキテクチャの根幹は次のとおり：

- 1リポジトリ／1Supabaseインスタンス／1 Web app／1 Admin app。
- 北海道版を新規リポジトリとして fork する（福岡市版と同じスタイル）。福岡市版を **ベース**とする（本家ではなく）。
- `scopes` テーブルで「北海道議会」「札幌市議会」「函館市議会」…「全179市町村議会」を表現。
- URLは `?scope=hokkaido`（デフォルト）／`?scope=sapporo` のようなクエリで切替、Cookieに永続化。

## 4. 北海道版の基本アーキテクチャ

### 4.1 リポジトリ戦略

- **新規リポジトリ `mirai-gikai-hokkaido` を福岡市版から fork**。
- 福岡市版の `kawasaki_schema_changes.sql`（地方議会化）は**そのまま継承**。
- 福岡市版の「単一自治体前提」を解除するため、**追加で `scopes` テーブルを導入し、既存の地方議会向けテーブルすべてに `scope_id` を付与**するマイグレーションを新規に積む。

### 4.2 「スコープ」の意味と粒度

| scope の例 | 種別 | 備考 |
|---|---|---|
| `hokkaido` | 都道府県議会 | デフォルト |
| `hokkaido-sapporo` | 政令市議会 | |
| `hokkaido-asahikawa` | 市議会 | |
| `hokkaido-nemuro` | 市議会 | |
| ... | 道内全179市町村議会 | 町村も含む |

- slug 規約：`hokkaido` ＋ `-{ローマ字市町村名}`。
- DB上のキーは UUID。slug は人間可読URL用。
- 「上位scope」概念は持たない（北海道議会と各市町村は同列。階層が必要になれば後付け）。

### 4.3 デフォルト挙動

- URL未指定／Cookieなし → `scope=hokkaido`（北海道議会）。
- セレクタで自治体を選択 → `?scope=hokkaido-sapporo` で遷移、同時にCookie `scope` に保存。
- 全主要ページ（議案一覧／議案詳細／レポート一覧／インタビューLP等）はscope-aware。

## 5. データモデル設計

### 5.1 新規 `scopes` テーブル

```sql
CREATE TYPE scope_kind_enum AS ENUM ('prefectural', 'municipal');

CREATE TABLE scopes (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  slug TEXT NOT NULL UNIQUE,               -- 'hokkaido', 'hokkaido-sapporo', ...
  display_name TEXT NOT NULL,              -- '北海道議会', '札幌市議会', ...
  kind scope_kind_enum NOT NULL,           -- prefectural | municipal
  prefecture_code SMALLINT NOT NULL,       -- 01..47（北海道版は常に 01）
  municipality_code TEXT,                  -- 総務省全国地方公共団体コード（5桁）。道議会は NULL
  sort_order INTEGER NOT NULL DEFAULT 0,
  is_active BOOLEAN NOT NULL DEFAULT true,
  council_base_url TEXT,                   -- 各自治体議会の公式トップURL
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

ALTER TABLE scopes ENABLE ROW LEVEL SECURITY;  -- ポリシー定義せず（CLAUDE.md規約）
```

- 初期投入は seed で道議会＋179市町村（slug/表示名/JIS市町村コード）を一括登録。
- データ未整備の市町村も**枠だけ用意**し、UI上は「準備中」を出す（後述）。

### 5.2 既存テーブルへの `scope_id` 追加

| テーブル | カラム追加 | 備考 |
|---|---|---|
| `council_sessions` | `scope_id UUID NOT NULL REFERENCES scopes(id)` | 福岡市版で diet_sessions から rename 済みのテーブル |
| `bills` | `scope_id UUID NOT NULL REFERENCES scopes(id)` | `council_session_id` 経由でも引けるが、検索高速化のため非正規化 |
| `committees` | `scope_id UUID NOT NULL REFERENCES scopes(id)` | 委員会構成は議会ごと |
| `factions` | `scope_id UUID NOT NULL REFERENCES scopes(id)` | 会派も議会ごと |
| `general_questions` | `scope_id UUID NOT NULL REFERENCES scopes(id)` | |
| `budget_overviews` | `scope_id UUID NOT NULL REFERENCES scopes(id)` | |
| `tags` | `scope_id UUID NULL REFERENCES scopes(id)` | NULL=全scope共通タグ、指定=scope固有 |
| `interview_configs` | （`bill_id` 経由で間接的にscope確定） | カラム追加は不要 |
| `chat_usage_events` | `scope_id UUID NULL` | コスト集計をscope別に出すなら |

`UNIQUE` 制約の見直し：
- `council_sessions(slug)` → `council_sessions(scope_id, slug)` に変更（slugは議会内で一意）
- `bills(slug)` → `bills(scope_id, slug)` に変更
- `factions(name)` → `factions(scope_id, name)` に変更
- `committees(name)` → `committees(scope_id, name)` に変更
- `faction_stances(bill_id, faction_id)` はそのままで良い（bill_id 経由でscopeが定まる）

### 5.3 `active_session` のスコープ別管理

福岡市版の `set_active_council_session()` は「is_active=true は1行だけ」の制約を全テーブル横断で持っているはず。これを **scope内で1行**に変更：

```sql
-- 部分ユニークインデックスで「scope内でアクティブは1つ」を保証
CREATE UNIQUE INDEX council_sessions_one_active_per_scope
  ON council_sessions(scope_id) WHERE is_active = true;
```

### 5.4 マイグレーション順序（提案）

1. `20260516xxxxxx_create_scopes_table.sql`（scopes 新設、scope_kind_enum 追加）
2. `20260516xxxxxx_add_scope_id_to_council_tables.sql`（council_sessions/bills/committees/factions/general_questions/budget_overviews に追加。既存データは「default scope=hokkaido」で埋める）
3. `20260516xxxxxx_relax_unique_constraints_for_multi_scope.sql`（UNIQUE再定義）
4. `20260516xxxxxx_seed_hokkaido_scopes.sql`（または seed スクリプトで投入）

注意：福岡市版のマイグレーションをすべて取り込んだ上で、その**後**に追加すること（順序を守らないとデータ移行できない）。

## 6. UI / ルーティング設計

### 6.1 セレクタ UI

| 配置 | 内容 |
|---|---|
| ヘッダー右寄せ（PC）／ハンバーガー内（SP） | 「議会を選ぶ」セレクトボタン。デフォルト「北海道議会」。クリックで全179自治体一覧（検索可・分類:都道府県／政令市／市／町／村）モーダル |

| 議案詳細・レポート詳細 | パンくず的に「北海道議会 ＞ 議案タイトル」など |

**179自治体すべてをドロップダウンで並べると操作性が悪い**ので、以下のUIを推奨：
- 上段：「北海道議会（道全体）」を目立たせて配置
- 下段：[政令市] [中核市] [一般市] [町] [村] のタブ／検索ボックス
- 各市町村クリック → そのscopeへ遷移

### 6.2 状態の保持

- URLクエリ `?scope=...` を**正**とする（共有・SEO・ブックマーク用）。
- middleware で URL → Cookie に同期（既存の `_applyDifficultyCookie` と同じ実装パターン）。
- ページ遷移時、リンクには現在のscopeを自動付与（後述の `routes.ts` で）。

### 6.3 `routes.ts` 復活と scope-aware 化

福岡市版で削除されたが、複数scopeを扱うなら必須。

```ts
// web/src/lib/routes.ts（新設）
import type { ScopeSlug } from "@/features/scope/shared/types";

export const routes = {
  home: (scope: ScopeSlug) => `/?scope=${scope}` as const,
  billDetail: (scope: ScopeSlug, billId: string) =>
    `/bills/${billId}?scope=${scope}` as const,
  billInterview: (scope: ScopeSlug, billId: string) =>
    `/bills/${billId}/interview?scope=${scope}` as const,
  // ... 既存ルートをすべて scope 必須にする
};
```

- URL構造は `/bills/[id]` のまま据え置き（scope は query で表現）。
  - パス階層化（`/[scope]/bills/[id]`）も検討したが、福岡市版／既存 admin との互換性、Next.js の動的セグメント数増による複雑化、preview link 整合などの理由で **query方式を推奨**。
- ただし `kokkai/[slug]/bills` のような国会専用パスは **撤去**（地方議会では `/sessions/[slug]/bills?scope=...` のような汎用パスに置換）。

### 6.4 `siteConfig` の動的化

福岡市版の「ファイル1個ハードコード」では複数scope共存ができない。北海道版では：

```ts
// web/src/config/site.config.ts（北海道版）
export const baseSiteConfig = {
  siteBaseName: "みらい議会",
  prefecture: "北海道",
  twitterHashtagBase: "みらい議会北海道",
  operator: { name: "（未定）", contactUrl: "", jurisdiction: "札幌地方裁判所" },
  features: { aiChat: false, aiInterview: false, showTeamMiraiSection: false },
};

// scope ごとの metadata はランタイムに合成
export function buildSiteConfig(scope: Scope) {
  return {
    ...baseSiteConfig,
    siteName: `${baseSiteConfig.siteBaseName}＠${scope.display_name}`,
    councilName: scope.display_name,
    councilBaseUrl: scope.council_base_url ?? "",
    cityName: scope.kind === "prefectural" ? baseSiteConfig.prefecture : scope.display_name,
  };
}
```

- ページ・OGP・metadata はサーバーコンポーネントで `getActiveScope()` → `buildSiteConfig(scope)` で動的生成。
- 各レイアウト／ページの `generateMetadata` で scope を読んで title/description を出し分け。

### 6.5 「データ未整備の自治体」の扱い

- scopes に登録はあるが議案が0件、というケースが大量に出る（179のうち大半）。
- 議案一覧ページで議案0件のとき、専用空状態：
  - 「○○市議会の議案データは現在準備中です。」
  - 「他の議会を選ぶ」リンク
- セレクタでも「データ整備済み」「準備中」のバッジを出す（`scopes` テーブルに `data_status` カラムを足してもいい）。

## 7. データ取り込み・MCP

### 7.1 MVP方針：手動入力 + MCP

- 既存の admin MCP ツール（`list_bills` / `create_bill` / `update_bill` / `update_bill_publish_status` / `create_diet_session` 等）を**scope対応**に拡張：
  - すべての引数に `scope_slug` か `scope_id` を必須化（または現在の active scope を context で渡す）。
  - `list_bills` 等は scope フィルタを必須化。
  - 福岡市版が `diet_sessions` を `council_sessions` に rename しているため、MCPツール名／responseスキーマも合わせて変更。
- Claude等のAIに「北海道議会の○○議案を登録して」と指示すれば、MCP経由でDBに入る運用を最初の体制とする。

### 7.2 後段の自動化に向けた下準備

- `scopes` テーブルに `council_base_url`（議会公式トップ）を持たせる → スクレイパーの起点になる。
- 福岡市版の `ai-collection` feature を雛形に、scope ごとのスクレイピング設定を切り出せる構造にしておく（ただしMVPでは実装しない）。
- 自動取得タイミングはVercel Cron／GitHub Actions cron のいずれかを後日選択。

### 7.3 議案番号・議会回次の表記揺れ

- 議会ごとに「令和8年第1回定例会」「平成31年第○○回臨時会」など表記揺れあり。
- `council_sessions.name`（人間可読）と `council_sessions.slug`（URL用）の二本立てを継続。
- `bills.bill_number`（福岡市版が追加）を流用。

## 9. 認証・権限

### 9.1 admin ロールと scope

- 本家：`raw_app_meta_data.roles=["admin"]` で全権限。
- 北海道版：当面これを踏襲（scope別の権限分離はMVP範囲外）。
- ただし将来「札幌市議会の編集権限だけ持つユーザー」を作りたくなる可能性が高いので、`raw_app_meta_data.allowed_scopes: ["hokkaido","hokkaido-sapporo"]` のような拡張を**設計上の余地として残す**。

### 9.2 RLS

- 本家規約どおり「RLS enable のみ、ポリシー定義せず、admin client 経由」を踏襲。
- scope別の認可ロジックは Server Actions / Loaders 側で実装。

## 12. 残論点（要追加判断）

実装着手前にユーザーに確認したい点：

1. **リポジトリ名**：`mirai-gikai-hokkaido` でよいか／別名希望か。GitHub organization も決めたい（`team-mirai` 配下？それとも別ハンドル？）。
2. **運営主体表記**：福岡市版の `operator.name = "バクモン"` のような運営者表記を、北海道版では誰の名前で出すか。
3. **AI機能の有無**：MVPで `aiChat` / `aiInterview` を有効にするか。福岡市版はいずれも `false`。
4. **チームみらいスタンス**：道議会・道内市町村議会のチームみらい所属議員のスタンスを表示するか／全 scope で `showTeamMiraiSection=false` でいくか。`factions` テーブルに「みらい」会派を入れるだけにとどめ、`mirai_stances` 相当の特別扱いはしない、で問題ないか。
5. **URL方式**：query方式（`?scope=...`）と path方式（`/[scope]/bills/...`）どちらにするか。本ドキュメントでは query方式を推奨したが、SEO・OGPでの優位性は path 方式の方が高い。
6. **scope の階層**：北海道議会 vs 道内市町村は同列で良いか／「北海道議会 → 札幌市議会」のような親子関係を持たせるか（議題横断検索など将来の拡張余地）。
7. **デフォルト挙動の地理判定**：ユーザーが北海道外からアクセスした場合もデフォルトは `hokkaido`（北海道議会）でよいか／「ようこそ」モーダルを出して選んでもらうか。
8. **既存 admin の `interview-simulation` `experts` feature の扱い**：福岡市版では削除されている。北海道版で復活させるか。
9. **データ整備の優先順位**：MVPリリース時点で投入完了している必要がある自治体（道議会＋政令市2つ程度？）の最低ラインを確認したい。
10. **デプロイ先・ドメイン**：Vercelか／独自ホスティングか。ドメイン候補（`mirai-gikai-hokkaido.jp` 等）。
11. **本家 mirai-gikai との同期方針**：本家のバグ修正・新機能を北海道版にも取り込みたいケースが発生する。福岡市版同様、本家 → 福岡市版 → 北海道版という伝言ゲームか、本家 → 北海道版 直接マージか。
12. **マルチ自治体運用の人的体制**：179自治体のデータ整備は誰が継続的に行うか（運営チームの体制設計が必要）。
