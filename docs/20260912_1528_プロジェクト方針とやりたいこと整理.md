# プロジェクト方針とやりたいこと整理

作成日: 2026-09-12

本ドキュメントは、本プロジェクトの位置づけ（思想）を明文化し、そこから降りてくる
「やりたいこと」を棚卸しして優先順位を付けるためのもの。
個別の実装計画はここでは書かず、塊ごとに別途設計文書を起こす。

## 1. 背景と位置づけ

### 1-1. これは何か

**高橋崇一郎 個人の CivicTech 活動**である。チームみらいの公式プロジェクトではない。
upstream（福岡市版／国政版の OSS）を土台にしているのは、自分の目的との親和性が
たまたま高かったからにすぎない。

- **プロダクト哲学**: 多様な民意を、議会に届け、反映する
- **立ち位置**: 意見を選別・代弁せず「届く場」を提供する**プラットフォーマー**

### 1-2. なぜ「脱・チームみらい色」なのか

党派色は、本プロジェクトの目的に対して**実務上の足かせ**になる。

- 議員・市長側に管理画面を使ってほしい（会派見解の記入、議案データの妥当性検証）
- 市民側からは党派を問わず声を集めたい

特定政党の色が付いていると、この両方が成立しない。
思想的な理由というより、**プロダクトが機能するための必要条件**として脱色する。

### 1-3. なぜ日系ベンダなのか

公共に近い領域を扱う以上、なるべく日系ベンダで動かしたいという個人の思想。
さくらインターネットは石狩にデータセンターを持ち、北海道に投資している事業者であり、
「札幌市議会版」という本プロジェクトの地域性とも一致する。

コスト判断ではなく、**何に金を払うかで立場を表明する**という選択。
これ自体が、同じ価値観の人と繋がるためのフックにもなる。

> **要ファクトチェック**: 発表・README に書く際は以下を裏取りすること。
> - 石狩DCの所在・規模、再生可能エネルギー利用の取り組み
> - ISMAP 登録は「さくらのクラウド」であって「さくらのVPS」とは別サービスの可能性が高い。混同しないこと

### 1-4. これを皮切りにしたい

本プロジェクトは単体の完成が目的ではなく、**これをきっかけに人と交流を持ち、
次に作るものを決めていく**ための第一歩。したがって:

- 完成度より**公開の早さ**を優先する
- 構成そのもの（AGPL・国内自前運用）が発信材料になる
- インフラは**このプロジェクト専用に固めず、共通基盤として組む**

## 2. 判断の原則（外部依存の線引き）

「日系ベンダで」を全てに適用すると GitHub も Claude Code も使えず破綻する。
以下の原則で線を引く。

> **市民から預かるもの**（インタビュー回答・意見・アクセスログ）は日本国内・日系事業者の管理下に置く。
> **作る側の道具**（GitHub、Claude Code、LLM API）は外部でよい。

これは実際の公共調達でも使われる線引き（データの所在 vs 開発ツール）であり、説明が通る。

| 依存 | 扱うもの | 判定 |
|---|---|---|
| ホスティング（Vercel） | 市民のリクエストが通る実行環境 | **移行**（さくらVPS） |
| Supabase（DB/Auth/Storage） | インタビュー回答＝市民の生の意見 | **移行**（VPS上にセルフホスト） |
| Google Analytics | 訪問者の行動ログ | **外す or セルフホスト解析** |
| Langfuse Cloud | プロンプトとLLM呼び出しログ | 無料枠に留める or 切る |
| **LLM API（OpenAI等）** | 推論のために意見が渡る | **例外。外部に出ることを明示する** |
| GitHub | ソースコード（公開物） | 外部でよい |
| ドメインレジストラ | — | 日系レジストラで一貫させる |

LLM だけが原則からはみ出る。ここは**はみ出していると自分で明示する**（プライバシーポリシーに記載）。
他を固めているからこそ、この1点の説明がしやすくなる。

## 4. A. リブランド

### 決定事項

- **プロジェクト名: オープン議会**（英名 OpenGikai）
- **ドメイン: `opengikai.tech`**

### 名前の選定理由

「議員が使っても政治的に安全と感じる中立性」を最優先制約とした。
「オープンガバメント＝情報公開」という枠組みは表立って反対しづらく、議員への説明が最もラク。
英語名がそのまま使えるため対外説明・将来展開にも効く。

温かみ・親しみやすさはサイトのコピーや UI で作れるが、
**名前が持つ政治的な含みは後から消せない**ため、中立性を優先した。

### `.tech` を選んだ理由

- 安価
- CivicTech と意味が合う
- **自治体公式と誤認されない**（`.jp` / `lg.jp` より明確に民間・非公式に見える）

非公式であることの明示が必要な本案件では、`.jp` より適している。
レジストラを日系にすれば事業者としての一貫性は保てる。

### ドメイン構造（マルチ自治体への逃げ道）

将来の道議会・他市町村対応は**設計に織り込まない**（スピード優先）。
ただし apex を取っておけば、必要になった時にサブドメインで割れる。**今やるのは apex 取得のみ**。

```

sapporo.opengikai.tech  → 将来分けたくなったら
hokkaido.opengikai.tech → 道議会版
```

サイト名は `web/src/config/site.config.ts` に既にある構造で「オープン議会 札幌市版」として出せる。

## 5. B. さくらVPSへのインフラ移行

### 決定事項

- **さくらVPS 2GB プラン 1台に全部載せる**（段階移行はしない）
- **VPS 上でビルドしない**
- **Supabase は最小構成でセルフホスト**
- **admin も VPS に載せる**（議員が使うため）＋ **ローカルにも同じ admin を立てる**
- 土台は「2個目のプロジェクトを足すのが簡単」を基準に組む

### なぜ段階移行しないか

当初「Phase 1: ホスティングのみ → Phase 2: DB移行」を検討したが撤回した。

1. 札幌市限定・低トラフィックなので、リスク分散のために段階を刻む必要が薄い
2. 半分だけ移行した状態は「日系で動かしている」という**説明が中途半端**になる
3. 未公開なので失敗しても誰も困らない。今が一番大胆に動ける

ただし**ローカルで docker compose を通して動作確認してから VPS に持っていく**。
VPS 上でいきなり試行錯誤しない。

### サイジング根拠

| 内訳 | 概算 |
|---|---|
| OS | ~200MB |
| Postgres（`shared_buffers` を絞る） | ~300MB |
| PostgREST + GoTrue（Goバイナリ） | ~80MB |
| storage-api | ~100MB |
| Next.js web（standalone） | ~250MB |
| Next.js admin（standalone） | ~250MB |
| nginx | ~20MB |
| **合計** | **~1.2GB** |

2GB で収まる。1GB は余裕が無さすぎるため非推奨。月1,700円前後（**要確認**）＋ドメイン年数千円。

> VPS は月単位契約で後からプランを上げられるはず。**プラン変更時にデータが引き継がれるか、
> 再インストールが必要かは契約前に確認すること**。

### 移行対象の棚卸し

#### ① ホスティング = Vercel → 移行難易度: 低

| 箇所 | 内容 |
|---|---|
| `.github/workflows/deploy_web.yml` | Vercel Deploy Hook を curl で叩くだけ |
| `web/src/app/(main)/layout.tsx:2,18` | `@vercel/speed-insights` |
| `web/next.config.ts` / `admin/next.config.ts` | `images.remotePatterns`（Supabase Storage 向け） |

**Edge Runtime を一切使っていない**（`export const runtime = "edge"` がゼロ）ため、
`next build && next start` を systemd で起こし nginx を前段に置けば動く。
`unstable_cache` は self-host の `next start` でもファイルシステムキャッシュとして機能する。
middleware も Node ランタイムで動作する。

注意点は `next/image` の最適化がサーバー CPU を食うこと（Vercel が肩代わりしていた部分）。
画像が少ないサイトなので `images.unoptimized` か nginx 配信でも実害は小さい。

#### ② DB / Auth / Storage = Supabase → セルフホスト

依存は3層。

1. **DB アクセス（PostgREST）** — 全 `repositories/` が `supabase-js` の `.from().select()` を使用。
   素の Postgres + Drizzle/Kysely に置き換えると全リポジトリ層の書き換えになる → **やらない**
2. **Auth（GoTrue）** — admin ログイン ＋ web の匿名ログイン
   （`web/src/features/chat/client/hooks/use-anonymous-supabase-user.ts:31` の `signInAnonymously`、
   チャットのレート制限／コスト管理に使用）
3. **Storage** — `bill-thumbnails` バケット
   （`admin/src/features/bills-edit/client/lib/thumbnail-storage.ts`）

Supabase は Apache-2.0 でセルフホスト可。**アプリ側の変更はほぼ環境変数の差し替えのみ**で済む。

立てるコンテナの取捨選択:

| コンテナ | 判断 |
|---|---|
| postgres / postgrest / gotrue | **必須** |
| kong | **不要**（nginx で代替） |
| studio | **不要**（SSHトンネルでローカルから） |
| realtime | **既に無効**（`supabase/config.toml:73`） |
| storage-api | 削れる可能性あり。用途が `bill-thumbnails` だけなので nginx 静的配信＋Server Action でのファイル保存に変えれば1つ減る。実装コストとのトレードオフ |
| imgproxy / analytics / vector | 不要 |

その他の対応:
- **匿名サインインを GoTrue 設定で有効化**する必要がある
- マイグレーションは `supabase` CLI の `--db-url` 指定で流せる

#### ③ AI = Vercel AI Gateway → 移行難易度: 低〜中

`gateway(AI_MODELS.gpt4o)` 形式で使用
（`web/src/features/chat/server/services/handle-chat-request.ts:101`、
`web/src/features/interview-session/server/services/handle-interview-chat-request.ts:219-220`）。

**AI Gateway は単なる HTTP API なので、VPS からでもそのまま動く**（機能的には壊れない）。
それでも切るなら:

- `packages/shared/src/ai/models.ts` のモデル ID が `"openai/gpt-4o"` という Gateway 形式なので、
  `openai("gpt-4o")` / `anthropic(...)` に振り分ける **resolver 関数を1つ作る**
- 既に DI 構造（`deps?.model ?? gateway(...)`）があるので差し込み口はある
- `web/src/lib/ai/calculate-ai-cost.ts` の価格テーブルが Gateway 形式キー前提のため、
  **キー体系は維持したままモデル解決だけ差し替える**

#### ④ Langfuse — 現状「落とせない」実装になっている

`web/src/lib/prompt/index.ts:23-31` の `createPromptProvider()` は、
Langfuse クライアントの初期化に失敗すると **throw する**。フォールバックが無い。

ただし同ファイルのコメントに「モック実装の追加手順」が明記されており、
`PromptProvider` インターフェースで抽象化済み。**ファイルベースの実装を1つ足すだけ**で切れる。

Langfuse のセルフホストは近年 ClickHouse + Redis + MinIO まで要るため、
**小さい VPS では論外**。選択肢は「クラウド無料枠に留める」か「実装して切る」の二択。

#### ⑤ Claude CLI 依存 — admin をローカルにも立てて回避

`admin/src/features/ai-collection/server/utils/execute-claude.ts:63` と
`admin/src/features/bills/server/actions/run-auto-feature.ts:34` が
`spawn("claude", ...)` でローカルの Claude Code CLI を叩いている。

> 補足: AIインタビュー機能は Claude ではなく Vercel AI Gateway 経由の GPT-5.2 系。
> Claude CLI 依存はこの2機能のみ。

**対応**: 同じ admin アプリを VPS とローカルの両方で起動し、DB を共有する。

- **VPS の admin** → 議員・出馬者・admin が使う。通常の編集作業
- **ローカルの admin** → admin 専用。Claude CLI 依存機能はここから実行
  （`pnpm dev:admin:prod-db` が既に存在）

Claude CLI 依存機能は admin ロール限定にすれば議員の画面には出ない。
VPS に Claude CLI を入れる必要もない。

### 共通基盤としての組み方

「作るものが未定」だからこそ、**土台をこのプロジェクト専用に固めない**。

- nginx は「vhost を1個足せばプロジェクトが増える」形にする
- **Postgres は共有インスタンス、プロジェクトごとに database を分ける**（メモリ節約が一番効く）
- デプロイは「GitHub Actions でビルド → rsync → systemd restart」というパターンを1つ作って使い回す
- 技術選択は徹底的に退屈にする。docker compose 1枚 + systemd + nginx。
  ひとりで未定の未来を運用するなら Kubernetes も凝った CD も敵
- バックアップは `pg_dump` を cron で回して手元か安いオブジェクトストレージへ

**2個目のプロジェクトを載せる作業が「vhost + systemd unit + database を足すだけ」になっていれば成功。**

## 6. C. 管理画面のロール権限

### 背景

議員・市長側に管理画面を使ってほしい。目的は2つ。

1. **議案データの妥当性検証と修正** — 当事者なので正確性が分かる
2. **会派見解の移譲** — 今は運営者が各会派の見解を書いているため
   「あの会派の見解は運営者の解釈だ」と言われうる。当の会派が自分で書けばその疑念が消える。
   **プラットフォーマーとして声を選別しないという立ち位置の、直接的な実装**

### 現状

**土台は既にある。**

- ロールは GoTrue の `app_metadata.roles` 配列（`admin/src/lib/auth/permissions.ts:7`）
- `checkEditorPermission` が「将来的に使用」というコメント付きで**空の器として存在**（同 :12-18）
- 招待機能が既にある（`admin/src/features/admins/server/actions/invite-admin.ts`）
  → **SMTP 設定は元々必要だった**

**足りないもの:**

- ページ・アクション単位のガード（今は `(protected)` レイアウトで一括保護しているだけ）
- パスワードリセット画面（`admin/src/app` に reset 系ルートが存在しない）
- **ユーザー管理テーブル**（`auth.users` と `get_admin_users()` 関数しかない）

### ロール定義

| ロール | 対象 |
|---|---|
| `admin` | 運営者本人。全権。**アカウント発行は admin のみ** |
| `legislator` | 議員。議案関連の編集＋自会派の見解編集 |
| `candidate` | 出馬者。閲覧のみ |

### 権限マトリクス

| 機能 | admin | 議員 | 出馬者 |
|---|:--:|:--:|:--:|
| 議案データの編集（妥当性検証・修正） | ○ | ○ | − |
| 自会派の見解 編集 | ○ | ○ | − |
| 他会派の見解 編集 | ○ | − | − |
| インタビュー要約レポート 閲覧 | ○ | ○ | ○ |
| インタビュー**生ログ** 閲覧 | ○ | ○ | ○ |
| 議案の公開/非公開 切替 | ○ | − | − |
| 会派・委員会・定例会マスタ | ○ | − | − |
| タグ管理 | ○ | − | − |
| AI情報収集 / 自動生成（Claude CLI） | ○ | − | − |
| アカウント発行・権限変更 | ○ | − | − |
| トピック分析の実行 | ○ | − | − |

### 決定事項と、その帰結

- **議案の編集は直接編集**（承認フローは設けない）。スピード優先。
  → だからこそ**変更履歴が必須**（後述）
- **公開/非公開の切替は admin のみ**。議員に渡すと「不利な議案を隠す」余地が生まれるため
- **インタビューは生ログも含めて議員・出馬者に開示する**
  → **市民への事前告知が必須**。「集計された傾向」ではなく
  **「あなたが書いた内容そのものが議員・立候補予定者に読まれる」と明示する**必要がある。
  `interview_messages`（生ログ）には個人が特定されうる記述が自然に混ざるため、
  アクセス制御ではなく**告知と同意**でカバーする設計になる

### 必須の追加実装

#### ① `admin_profiles` テーブルの新設

会派見解のスコープ制限（自会派のみ編集可）には**ユーザーと会派の紐付け**が要る。
現状 DB にユーザー管理テーブルが無いため新設する。
`app_metadata` に押し込むより、SQL で引けて外部キーが張れるこちらが扱いやすい。

```sql
create table public.admin_profiles (
  user_id uuid primary key references auth.users(id) on delete cascade,
  role text not null check (role in ('admin','legislator','candidate')),
  faction_id uuid references public.factions(id),  -- legislator のみ
  display_name text not null,
  created_at timestamptz not null default now()
);
alter table public.admin_profiles enable row level security;  -- ポリシーは定義しない
```

既存の `checkAdminPermission` / `checkEditorPermission` はこれを見る形に書き換える。

#### ② 変更履歴（監査ログ）

議員が議案データや会派見解を編集できるなら、**誰がいつ何を変えたかが追える**必要がある。

理由は不正防止よりも**疑念の防止**。
他会派から「A党が議案の説明を書き換えたのでは」と言われた時、履歴が無いと反証できない。
**中立プラットフォームを名乗る以上、実質必須。**

#### ③ 権限ガードの実装

- ページ単位の分岐: `bills` / `bills-edit` は議員OK、
  `factions` / `committees` / `admins` / `tags` / `ai-collection` は admin のみ
- ナビゲーションの出し分け
- **Server Action 側にもガードを入れる**（UI を隠すだけでは不十分）

#### ④ パスワードリセット画面

GoTrue の `resetPasswordForEmail` ＋ リセット用ルートを新規実装。

#### ⑤ SMTP

GoTrue のメール送信先。招待・パスワードリセットの両方で必要。
さくらのメールボックス等、日系で寄せられる。
