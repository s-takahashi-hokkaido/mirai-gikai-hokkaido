## 2. 現状コードとの食い違い

### 2-1. `detectBillType()`（`parse-bill-table.ts`）✅ 解決済み

現状の判定ロジック:

```ts
function detectBillType(
  numberText: string
): "bill" | "consultation" | "opinion" | "petition" | "appeal" | "report" | null {
  if (numberText.startsWith("議案")) return "bill";
  if (numberText.startsWith("諮問")) return "consultation";
  if (numberText.startsWith("意見書案")) return "opinion";
  if (numberText.startsWith("請願")) return "petition";
  if (numberText.startsWith("陳情")) return "appeal";
  if (numberText.startsWith("報告")) return "report";
  return null;
}
```

全6種別に対応済み。請願（`petition`）と陳情（`appeal`）は別値に分離された。

---

### 2-2. スクレイパーのスキップ処理（`parse-bill-table.ts`）❌ 未対応

現状:

```ts
if (!type || type === "petition" || type === "appeal" || type === "report") continue;
```

**DB に保存されるのは `bill` / `consultation` / `opinion` の3種別のみ。**

**問題点**:
- `petition`（請願）・`appeal`（陳情）・`report`（報告）を一律スキップしている
- 陳情は1回の定例会で90件と多く、市民の声を可視化する観点で対応価値が高い

**修正案**: どの種別を保存するか方針を決めてからスキップ条件を更新する。
候補方針:
  - A. 全種別を保存する（`if (!type) continue;` のみにする）
  - B. 報告だけスキップ、それ以外は保存する（報告は採決なし・閲覧ニーズ低め）
  - C. 種別ごとにフラグで制御する

### 2-4. `bills.status` の表現（種別ごとの議決結果）❌ 未対応

現状の `mapResultToStatus()`:

```
「可決/同意/承認/採択/棄却」→ approved   ← ⚠️ 棄却は rejected が正しい
「否決/不採択」             → rejected
その他                      → submitted
```

**問題点**: 種別によって結果の呼び方が異なるのに、一律 `approved` に畳んでいる。また `棄却` は請願の却下を意味するため `rejected` にマップすべきところ誤って `approved` になっている。

| 種別 | 本来の結果表現 | 現状 |
|---|---|---|
| 議案（条例・予算等） | 可決 / 否決 | approved / rejected |
| 議案（決算） | 認定 / 不認定 | approved に畳まれる |
| 議案（人事） | 同意 / 不同意 | approved に畳まれる |
| 請願・陳情 | 採択 / 不採択 / 継続審査 | adopted / rejected |
| 専決処分 | 承認 | approved に畳まれる |
| 請願（却下） | 棄却 | 誤って approved にマップされている |

**根本原因**: `bill_type` の粒度が粗すぎて `bill_type` × `status` だけでは表示名が一意に決まらないため、`status_note`（スクレイパーが取得した元テキスト）に頼らざるを得ない設計になっている。

**あるべき設計**: `bill_type` を細かく切ることで `bill_type` × `status` → 表示名 が決定的になり、`status_note` を表示目的で使う必要がなくなる。

### 実際のデータから導いた完全な `bill_type` 分類

公式サイト（第1回・第2回定例会）の全議案を調査した結果:

| bill_type | 内容 | 議決結果の表現 | 自動判定方法 |
|---|---|---|---|
| `bill` | 条例・予算・補正予算・契約・財産・市道認定等 | 可決 / 否決 | 番号「議案」＋それ以外 |
| `bill_settlement` | 決算認定（第3回定例会に多い） | 認定 / 不認定 | 件名に「決算」を含む |
| `bill_personnel` | 人事同意（選任・委嘱・任命） | 同意 / 不同意 | 件名に「選任」「委嘱」「任命」を含む |
| `bill_ratification` | 専決処分承認（議案として提出される） | 承認 / 否決 | 件名に「専決処分承認」を含む |
| `consultation` | 諮問（行政不服審査等） | （意見を答える） | 番号「諮問」 |
| `opinion` | 意見書案（議員提出） | 可決 / 否決 | 番号「意見書案」 |
| `resolution` | 決議（議員提出） | 可決 / 否決 | 番号「決議」 |
| `petition` | 請願（市民要望・議員紹介あり） | 採択 / 不採択 / 継続審査 / 棄却 | 番号「請願」 |
| `appeal` | 陳情（市民要望・議員紹介不要） | 採択 / 不採択 / 継続審査 | 番号「陳情」 |
| `report` | 専決処分報告・繰越計算書等（採決なし） | なし | 番号「報告」 |

※ `bill_settlement`・`bill_personnel`・`bill_ratification` は番号が全て「議案」で始まるため、件名テキストでの二次判定が必要。
※ `bill_settlement` 等のスキーマへの追加には CHECK 制約の更新マイグレーションが必要。

### `bill_type` × `status` → 表示名マッピング（あるべき姿）

```
bill             × approved → 可決      bill             × rejected → 否決
bill_settlement  × approved → 認定      bill_settlement  × rejected → 不認定
bill_personnel   × approved → 同意      bill_personnel   × rejected → 不同意
bill_ratification× approved → 承認      bill_ratification× rejected → 否決
opinion          × approved → 可決      opinion          × rejected → 否決
resolution       × approved → 可決      resolution       × rejected → 否決
petition         × adopted  → 採択      petition         × rejected → 不採択 / 棄却
petition         × carried_over         → 継続審査
appeal           × adopted  → 採択      appeal           × rejected → 不採択
appeal           × carried_over         → 継続審査
consultation     × （該当なし）
report           × （採決なし）
```

このマッピングが実装されれば `status_note` は表示目的で不要になり、フリーテキストのメモ欄に降格できる。

**現状UIの問題**:
- 一覧バッジ（`bill-status-badge.tsx` / `bill-status.ts`）: `status` enum のみ参照。`bill_type` も `status_note` も見ていないため `approved` は一律「可決」表示
- 詳細プログレス（`bill-status-progress.tsx`）: `status_note` を補足テキストとして表示するが、メインラベルは `STATUS_LABELS[status]`（= "可決"）のまま
- `getCardStatusLabel()` が `bill-status.ts` と `bill-status-badge.tsx` の2箇所に重複定義されており、ラベルの内容も微妙に異なる（「議会審議中」vs「委員会審査中」）

### 5-1. 本来あるべき審議フローと取得可否

| ページ | 取得できる情報 | ステータス判定への有用性 |

| 議案一覧（giantouichiran） | 提出日・議決日・結果テキスト | `submitted` か最終結果のみ |

### 5-2. 現状 enum の実態


- `in_committee` / `plenary_session` を enum から削除するか、「手動設定用」と明記するかを決める

## 6. スクレイパーの今後の方針

### 6-1. 現状の問題整理

現状スクレイパー（`scrape-bills.ts` + `parse-bill-table.ts`）は議案一覧HTMLのテーブルだけを読んでいる。
これで取れるのは「骨格データ」のみで、審議の実体（質疑内容・中間状態・委員会付託の経緯）は取れない。

会議録スクレイパー（Phase 2）は `gijiroku.com` CGI APIを利用しているが、APIが非公式で仕様が安定しているか不明。

### 6-2. しばらくは手作業 + Claude方式が現実的

| 方式 | 向いている場面 | 課題 |
|---|---|---|
| 自動スクレイパー | 定型テーブルデータ（議案一覧・基本メタデータ）の定期取得 | 中間状態・詳細内容は取れない |
| 手作業 + Claude | PDF（議案本文・会議録）をClaudeに食わせて構造化 | スケールしない（会期が増えると工数増） |

**当面の方針（案）**:
- 議案の基本メタデータ（番号・名前・日付・最終結果）はスクレイパーで自動取得
- 議案内容・質疑内容・中間状態は PDF や会議録を手動ダウンロードして Claude で構造化
- 精度と運用感を確認しながら、自動化できる部分を段階的にスクレイパーへ移行

**将来的な自動化の優先候補**:
1. 議案一覧の全種別取得（§2-2 のスキップ解除で対応可能）
2. 会議録の自動取得（gijiroku.com CGI の安定性次第）
3. 委員会付託情報の自動取得（現状はページ構造上困難）

## 7. 議員・会派データ

### 7-1. 議員マスタ（`council_members` テーブル）が存在しない ❌ 未対応

現状、議員は各テーブルに名前文字列として埋め込まれているだけで、正規化されていない。

| テーブル | 議員が登場する箇所 |
|---|---|
| `bill_discussions` | `questioner_name`（文字列）, `questioner_party`（会派名・文字列） |
| `general_questions` | `questioner_name`（文字列）, `questioner_party`（会派名・文字列） |

**問題点**:
- 表記ゆれ（例: スペース有無・旧姓等）で同一議員が別人として扱われる
- 議員ごとの質疑一覧・選挙区・会派所属などの横断検索ができない
- 会派移籍が発生した場合、過去データへの影響を追えない

**修正案**: `council_members` テーブルを追加し、議員マスタを正規化する。
`questioner_name` から FK（`questioner_member_id`）で紐づけるか、名前テキスト照合で後付けマッピングするかは設計時に決める。

テーブル設計案:

```sql
create table council_members (
  id         uuid primary key default gen_random_uuid(),
  name       text not null,           -- 正式表記
  kana       text,                    -- 読み仮名
  faction_id uuid references factions(id),
  district   text,                    -- 選挙区（行政区）
  is_active  boolean default true,
  created_at timestamptz default now()
);
alter table council_members enable row level security;
```

データ投入は公式の会派別名簿（`meibo-kaiha.html`）をスクレイプするシードスクリプトが必要。
既存の `factions` シードと合わせて実装するのが自然な流れ。

### 7-2. `factions.alternative_names` が未活用 ❌ 未対応

現状: カラムは定義済みだが、会議録スクレイパー（`scrape-minutes.ts` / `parse-minutes.ts`）での名寄せロジックが未実装。

**問題点**:
- 会議録上の会派名が公式名と異なる略称で記載された場合、`questioner_party` と `factions.name` が不一致になる
- 例: 「民主市民連合」→「民主」「民市連」、「自由民主党」→「自民」等

**修正案**: `parse-minutes.ts` で `factions` の `name` と `alternative_names` を参照して正規化する関数を追加する。
`alternative_names` への略称登録はシード時またはAdminで行う運用にする。

## 8. 委員会会議録の取得未対応

> 調査日: 2026-05-31 / 調査対象: `sapporo.gijiroku.com` CGI API・公式サイト

### 8-1. gijiroku.com の会議種別（KGTP）と公開状況

`scrape-minutes.ts` は `KGTP=1`（本会議）しかリクエストしていないが、実際には委員会の会議録も同システムで公開されている。

| KGTP | 種別 | 2025年の件数 | 現状 |
|---|---|---|---|
| `1` | 本会議 | 多数（定例会×複数日） | ✅ スクレイプ対象 |
| `2` | 議案審査特別委員会（推定） | 3件（R7第1回 4/2〜4/3） | ❌ 未取得 |
| `3` | 常任委員会・議会運営委員会・各種特別委員会 | **137件** | ❌ 未取得 |

### 8-2. 公式サイトでの PDF 公開（速報版）

`https://www.city.sapporo.jp/gikai/html/kaigiroku-sokuho.html` にて、常任委員会6つ＋調査特別委員会2つの会議録が **PDF 形式**で別途公開されている。gijiroku.com と二重に公開されている可能性がある。

### 8-3. 対応方針（案）

- **gijiroku.com 経由**: `KGTP=3` を追加すれば既存スクレイパーの延長で取得できる。ただし `scrape-minutes.ts` は現状「代表質問（本会議）」専用の構造のため、委員会対応には設計変更が必要。
  - 会議ごとに `committee_id` を紐づける処理が必要（会議名→委員会のマッピング）
  - 委員会質疑の格納先は `bill_discussions`（議案に紐づく質疑）になる想定
- **PDF 経由**: 公式サイトの PDF を Claude で構造化する手動運用も選択肢。gijiroku.com の CGI が不安定な場合のフォールバックとして機能しうる。

**優先度**: 低〜中（本会議データが充実してから着手が現実的）
